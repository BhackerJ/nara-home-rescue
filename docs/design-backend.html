1 · 系统结构

一台电脑上五个进程，外加两个托管服务。ServiceCase actor 是工单流程唯一的真相来源；两个 runner（coordinator、provider）只执行，不留状态，彼此只通过 Relay 说话。

调用（HTTP / pg / API）Relay 消息拔电源（SIGKILL）

2 · 一个工单从报修到确认

只演一次故障：发出时段请求后拔电源。维修商和 Relay 照常运行；新 coordinator 从 actor 读回进度、从 Relay 补拉错过的拒绝，诊断不重做。网页显示的每一步都是 actor 里存下的事件。

调用Relay 消息调不通 / 进程不在

3 · 发件箱：coordinator 发一条消息的固定顺序

第 1、2、4 步都走这六步。在任何一处崩溃，恢复后都不会重复。

1读 ServiceCase

这一步已经完成，就跳过

2查发件箱

已有这一步的消息（上次没来得及发），跳到第 4 步

3stageStep

算出结果，连同消息原文写进发件箱（带 expectedRevision）

4原样发出

idempotencyKey = <caseId>:<step>，Relay 按 key 返回同一条

5completeStep

记下 relayMessageId，清发件箱，status 改成等维修商

6预设了拔电源？

记 plug_pulled，调 supervisor /pull-plug

为什么不会重复
  • 消息没发出去 → 重算一次
  • 发出去了没记录 → 原样重发，Relay 按 key 返回原来那条（同 key 不同内容报 409）
  • 已经记录的步骤 → 直接跳过
  • 预约另由 ProviderCalendar 按 <caseId>:book 防重复，key 重复时记一条事件，界面上看得见
provider 处理一条消息
  • claim(messageId)：处理过就直接返回
  • 查排期或预约 → 模板回复，key <caseId>:provider:<kind>
  • markReplied(messageId, replyMessageId)
  • 启动时先 messages.list，补处理死掉期间到达的请求

出错统一处理：outcome_unknown、连接被拒、revision 不匹配、Relay 发送失败，一律退避（200ms 起翻倍，最多 2 秒）后重读 actor 重进循环；连续 20 次失败把工单设成 failed。
